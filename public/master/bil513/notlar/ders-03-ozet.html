Answer pattern#

  • First name the shared object, its operations and the invariant, then choose the tool sl. 4; Okuma §17.
  • Trace in the lecture's model: individual reads and writes are atomic, execution is sequentially consistent. Say "this is not a promise about racy C" sl. 5.
  • A trace shows a possible execution. "Six abstract schedules, not six equally likely executions": never infer a probability from an enumeration sl. 9.
  • "One correct execution does not prove correctness for every allowed interleaving" sl. 7. "Testing samples executions. Invariants and ordering explain why…" sl. 68
  • For a protocol, check safety (mutual exclusion) and liveness (progress, bounded waiting) separately. State the scheduler and termination assumptions sl. 14–15.

Definitions in one line each#

  • Race condition: a correctness failure that depends on timing or ordering sl. 11.
  • C data race: conflicting accesses in different threads, at least one non-atomic, without the required ordering → undefined behaviour sl. 11.
  • Invariant: what valid shared state means, e.g. 0 ≤ count ≤ capacity, A + B constant during a transfer sl. 12.
  • Critical section structure: entry section → critical section → exit section → remainder sl. 13.
  • Mutual exclusion: no two participants execute conflicting critical sections together sl. 14.
  • Progress: when the section is free and requests exist, choosing the next entrant cannot be postponed indefinitely sl. 14.
  • Bounded waiting: after a request, there is a bound on how many others can enter first sl. 14.
  • Safety: something bad never happens. Liveness: useful progress eventually happens sl. 15.
  • Deadlock: participants wait for events that only the blocked participants can cause. Starvation: one participant is perpetually denied progress while others continue. Livelock: participants keep reacting or retrying without completing useful work sl. 62. Classify by dependency, not by whether the CPU is busy: a deadlock with spinning waiters also burns CPU.
  • Priority inversion: H waits for a lock held by L; M delays L and therefore H. Priority inheritance temporarily raises L sl. 63.

Mechanisms and protocols#

  • Strict alternation sl. 16: enter only when turn == i; on exit give the turn to the peer. Mutual exclusion holds, progress fails: a thread that wants to enter twice in a row waits for a peer that may never want to enter.
  • Peterson sl. 17–18: flag[i] = true; turn = j; while (flag[j] && turn == j) ; CS; flag[i] = false. If both flags are true, the last writer of turn waits. Satisfies all three requirements under the model; it is "reasoning pseudocode, not a safe copy-and-paste C implementation" sl. 17. Swapping the order of the flag and turn writes breaks mutual exclusion sl. 19.
  • Test-and-set atomically returns the old value and sets the flag. CAS(lock, 0, 1) returns the old value: the thread that gets 0 owns the lock, the thread that gets 1 does not and retries. "A simple retry loop does not itself guarantee bounded waiting" sl. 20–21.
  • Mutex sl. 25–29: acquire before touching protected state, release after restoring the invariant; the acquirer unlocks. Coarse lock = easier reasoning, more serialization. Keep the check and the dependent update together inside the lock; do independent work and long I/O outside it.
  • Spin vs block sl. 30: spinning may suit a very short wait when the owner runs on another CPU; blocking avoids wasting a CPU on longer waits.
  • Semaphore sl. 36–39: permits. wait consumes one or blocks; post adds one. Pool of 3 → initialize to 3. Initialization ordering → ready = 0; the initializer posts, the user waits.
  • Condition-wait protocol sl. 44: lock → check predicate → while false wait → operate → unlock. pthread_cond_wait atomically releases the mutex and waits, and returns with the mutex reacquired.
  • Signalling sl. 45: change the predicate while holding the same mutex, then notify. This is POSIX/Mesa style: the woken thread must reacquire the mutex. A Hoare-style monitor hands control to it immediately ek bilgi: "Hoare" adı OSTEP'ten.
  • Lost wakeup sl. 47: checking "empty" without the mutex, then the producer inserts and signals, then the consumer sleeps. Fix: test under the same mutex and use the atomic release-and-wait. "The state, not a remembered signal, decides whether to sleep."
  • Bounded buffer with semaphores sl. 51–52: empty = N, full = 0, mutex = 1.
  • Producer: wait(empty); wait(mutex); insert; post(mutex); post(full).
  • Consumer: wait(full); wait(mutex); remove; post(mutex); post(empty).
  • Reserve the permit before taking the mutex. In the reverse order, a consumer holding the mutex while waiting for full blocks the producer → deadlock.
  • Bounded buffer with CVs sl. 54: one mutex; producers wait while count == N, consumers wait while count == 0.
  • Closing a queue sl. 55: set closed under the mutex after the producer finishes. Consumers wait while count == 0 && !closed. If closed and empty, exit; otherwise drain. Broadcast on closure.
  • Readers–writers sl. 56: many readers or one writer. Reader preference can starve writers.
  • Dining philosophers sl. 57–61: everyone takes the left chopstick → circular wait → deadlock. Lower-numbered chopstick first breaks the cycle (it does not prove fairness). Monitor solution: THINKING/HUNGRY/EATING states under one lock; a philosopher eats only if neither neighbour is eating.

Choosing the tool sl. 64#

Need Tool
One invariant across several operations mutex
A limited number of permits counting semaphore
Wait until shared state satisfies a predicate condition variable + mutex
One independent numeric update atomic operation (fetch-add)
Always minimize shared mutable state, then specify the remaining protocol
