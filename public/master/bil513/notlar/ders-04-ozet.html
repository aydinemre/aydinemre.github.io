Answer pattern#

  • State the resource model first: types and instance counts, current allocations, outstanding requests, release assumptions. Then pick the question Okuma §17.
  • Pick the right test: a current single-instance cycle supports a deadlock diagnosis; a multi-instance state needs counts and reduction; a maximum-demand grant question needs a safety test Okuma §17.
  • For every answer: state the assumptions, show a graph or vector trace, and say what the method does not guarantee sl. 73.
  • When you say "it depends", name the exact model assumption that changes the result Okuma §17.
  • Separate a proof about a protocol from evidence from one execution sl. 2.

Key definitions#

  • Four necessary conditions sl. 9: mutual exclusion, hold and wait, no preemption, circular wait.
  • Deadlock: a set cannot progress because the events they need depend on blocked members of that set. Starvation: one waits indefinitely while other work continues. Livelock: states change, useful work never completes sl. 15–16.
  • RAG sl. 17: T → R is a current request; R → T is an allocated instance. Dashed T ⇢ R is a future claim, not a blocked request sl. 21, 44.
  • Wait-for graph (single instance only): replace Ti → R → Tj with Ti → Tj sl. 24.
  • Safe: at least one order satisfies every remaining maximum demand sl. 39.

The four approaches sl. 27#

Approach Decision Information Cost
Prevention forbid a necessary condition (lock order, whole-set reservation) the protocol; no per-thread maxima restrictions on access
Avoidance grant only if the state stays safe declared Max, Allocation, Available maximum-demand information, conservative refusals
Detection + recovery allow, detect, repair current Request, consistent snapshot, rollback boundary monitoring and lost work
Accept the risk no general mechanism — the application handles failures

Formulas and steps#

Banker's safety test sl. 47–50:

  1. Need = Max − Allocation (maximum additional demand).
  2. Work = Available; all Finish = false.
  3. Find unfinished i with Need[i] ≤ Work in every component. Work = Work + Allocation[i] (not Max: Work − Need + Max = Work + Allocation). Repeat.
  4. All finished → safe. Stuck → unsafe. Final Work must equal the total vector.

Request check sl. 51:

  1. Request ≤ Need? else error (exceeds declared maximum).
  2. Request ≤ Available? else wait (unavailable).
  3. Tentatively: Available −= R; Allocation += R; Need −= R.
  4. Safety test on the tentative state: commit if safe, else restore and wait. Serialize decisions.

Detection sl. 57–58: same reduction with Request instead of Need; threads with zero Allocation start finished; unfinished holders = deadlocked set; report zero-allocation waiters separately.

Invariant sl. 72: total = Available + Σ Allocation in every component.

Cost sl. 62: matrix detection O(m·n²); graph cycle detection O(V + E) with adjacency lists.

Lock-order proof sl. 31: a cycle would need rank(L1) < rank(L2) < … < rank(Lk) < rank(L1), which is impossible. Assumes every path follows the order (callbacks, error paths); does not prove fairness.
