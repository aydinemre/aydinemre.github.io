S1 (kısa cevap, kolay) — sl. 13#

Kritik bölge yapısının dört parçasını (entry, critical section, exit, remainder) tanımlayın. Hangi kritik bölgelerin birbiriyle çakıştığını ne belirler? İlgisiz iki kaynak aynı kilidi paylaşmak zorunda mı?

Cevabı ve ölçütü göster

Cevap (ideal). Entry section: requests permission. Critical section: operates on the protected shared state. Exit section: releases permission. Remainder: independent work done without retaining the lock. The protected resource determines which critical sections conflict: sections that touch the same shared state (the same invariant) must exclude each other. Unrelated resources can use different locks; one global lock is not required, although a coarse lock is easier to reason about sl. 29.

S2 (doğru/yanlış + gerekçe, kolay) — sl. 10, 22#

"Bir sonraki boş süreç kimliğini (next_available_pid) atomik olarak okumak, o kimliği rezerve etmek için yeterlidir."

Cevabı ve ölçütü göster

Cevap (ideal). False. Reading is not reserving. Two requests can both atomically read the same next identifier and both hand it out. The check and the reservation must be one coordinated step: a mutex around read-and-advance, or a single atomic read–modify–write such as fetch-add. The lecture presents this as a conceptual failure scenario, not as evidence that current Linux fork() allocates duplicate live PIDs.

S3 (kısa cevap, kolay) — sl. 23–24#

Benzincideki tuvalet anahtarı benzetmesi mutex'in hangi kurallarını gösterir? Benzetmenin varsaydığı iki şeyi ve uzun sopanın garanti etmediği iki şeyi yazın.

Cevabı ve ölçütü göster

Cevap (ideal). It shows ownership: one key, one owner; take the key before entering, keep it for the whole visit, return it when leaving (lock, critical section, unlock). Assumptions: taking the key is indivisible (checking that it is on the hook and claiming it are not separate competing steps); there is one usable key and no other entrance, and everyone follows the procedure. Returning it early exposes an occupied resource; forgetting it prevents later access. The long stick only discourages losing the key: it does not guarantee fair admission (no queue, bounded waiting), does not prevent a duplicate key, and does not enforce the protocol.

S4 (iz, kolay–orta) — sl. 8–9#

Üç thread (A, B, C), sayaç 0. Her biri bir artırma yapıyor: oku (R), sonra oku + 1'i yaz (W). (a) Kaç farklı interleaving vardır? (b) Mümkün son değerler nelerdir? (c) Son değeri 1 yapan bir çizelge ve 2 yapan bir çizelge verin.

Cevabı ve ölçütü göster

Cevap (ideal). (a) Six steps, two per thread: 6! / (2! 2! 2!) = 90 schedules. (b) {1, 2, 3}. (c) Final 1: A:R0, B:R0, C:R0, A:W1, B:W1, C:W1 (all three read 0 before any write). Final 2: A:R0, A:W1, B:R1, C:R1, B:W2, C:W2 (B and C both read 1). Final 3 only in the 3! = 6 fully serialized schedules. These are possible outcomes, not probabilities.

S5 (iz, orta) — sl. 8#

x = 1. A thread'i x = x + 1, B thread'i x = x * 2 yapıyor; her biri oku, sonra yaz. Altı interleaving'in her birinin sonucunu yazın. Hangi sonuç seri yürütmelerden hiçbirinde çıkmaz?

Cevabı ve ölçütü göster

Cevap (ideal). AABB: A reads 1, writes 2; B reads 2, writes 4 → 4. BBAA: B reads 1, writes 2; A reads 2, writes 3 → 3. ABAB: both read 1; A writes 2; B writes 2 → 2. ABBA: both read 1; B writes 2; A writes 2 → 2. BAAB → 2. BABA → 2. Results {2, 3, 4}. Serial executions give 4 (A then B) or 3 (B then A); 2 appears only when both read the old value 1 and one update is lost.

S6 (değer izi, orta) — sl. 36, 38#

Üç yazıcılık bir havuz S = 3 ile korunuyor. J1, J2, J3, J4, J5 sırayla wait yapıyor. Sonra sırayla J2 post, J1 post, J3 post ediyor; ardından yeni sahipler de işini bitirip post ediyor. Her adımdan sonra S'yi ve bloklu işleri yazın. J2 post ettiğinde yazıcıyı kim alır?

Cevabı ve ölçütü göster

Cevap (ideal). 3 → J1: 2 → J2: 1 → J3: 0 → J4 blocks (S = 0) → J5 blocks (S = 0). J2 posts: a permit becomes available and one waiter (J4 or J5) acquires it; S stays 0. Which one is not determined by J2 and FIFO is not assumed. J1 posts: the other waiter acquires; S = 0. J3 posts: S = 1. The two later owners post: S = 2, then 3. Every successful acquisition has a matching release, so the count returns to the pool size.

S7 (doğru/yanlış + gerekçe, orta) — sl. 39, 44, 47#

"Kimse beklemiyorken yapılan pthread_cond_signal saklanır; sonra pthread_cond_wait çağıran ilk thread hemen döner. Bu yüzden predicate değişkenine gerek yoktur."

Cevabı ve ölçütü göster

Cevap (ideal). False. A condition-variable notification is not a stored permit: if nobody is waiting it has no effect, and a later waiter sleeps. Waking also does not mean the condition holds (another thread may change the state first; spurious wakeups are permitted). The predicate lives in shared application state, protected by the mutex; the waiter checks it under the mutex in a while loop. The memory-of-posts behaviour described belongs to a semaphore, not to a condition variable.

S8 (kod okuma, orta) — sl. 45, 54#

Bir üretici şöyle yazılmış:

pthread_mutex_lock(&m);
while (count == N) pthread_cond_wait(&not_full, &m);
pthread_cond_signal(&not_empty);     /* signal BEFORE inserting */
buffer[in] = item; in = (in + 1) % N; count++;
pthread_mutex_unlock(&m);

Tüketiciler kilit altında while (count == 0) ile bekliyor. Bu üretici yanlış mı?

Cevabı ve ölçütü göster

Cevap (ideal). It is still correct. The awakened consumer must reacquire the mutex before returning from pthread_cond_wait, and the producer holds the mutex until after it has inserted the item and incremented count. By the time any consumer can recheck the predicate, the state change is complete; and the consumer rechecks with while anyway. What matters is that the predicate is changed while holding the same mutex and that waiters recheck after reacquisition. (Signaling after the update is the clearer convention sl. 54.)

S9 (hatayı bul, orta) — sl. 39–40; OSC ch6 sl. 41#

mutex adlı bir semaphore (ilk değer 1) iki farklı yerde yanlış kullanılmış:

/* (a) */ wait(mutex);  /* critical section */  wait(mutex);
/* (b) */ signal(mutex); /* critical section */ wait(mutex);

Her birinin sonucunu açıklayın.

Cevabı ve ölçütü göster

Cevap (ideal). (a) The second wait should have been a signal. The thread consumes the only permit on entry; at exit it waits again with value 0 and blocks forever. Every other thread also blocks on entry: no one can ever enter again (a progress failure; the semaphore has no owner that could detect the mistake). (b) The thread posts before entering: the value becomes 2. The faulty thread is inside without holding a permit, and two more threads can pass wait, so up to three threads can be inside the critical section together: mutual exclusion is violated; the final wait then removes a permit that was never acquired, leaving the count inconsistent with the resource. Both show that a semaphore enforces exclusion only when the program uses it correctly.

S10 (tasarım, orta) — sl. 64, 36, 54#

Bir yazdırma sunucusu tasarlıyorsunuz: (1) iki fiziksel yazıcı var, en fazla iki iş aynı anda yazdırılabilir; (2) gelen işler en fazla 8 iş tutan bir kuyruğa giriyor, işçiler kuyruk boşken uyumalı; (3) "toplam yazdırılan sayfa" istatistiği tutuluyor. Her parça için aracı seçin ve neden seçtiğinizi yazın.

Cevabı ve ölçütü göster

Cevap (ideal). (1) A counting semaphore initialized to 2: a limited number of interchangeable permits; wait before using a printer, post after. (2) A bounded buffer: one mutex protecting the queue fields (array, in, out, count) and two condition variables, not_full (producers wait while count == 8) and not_empty (workers wait while count == 0), with while loops; alternatively semaphores empty = 8, full = 0 plus a mutex, reserving the permit before taking the mutex. A closing protocol is needed if the server shuts down. (3) An atomic fetch-add: one independent numeric update. If the statistic had to stay consistent with other fields (e.g., pages per job in a table), it would belong under the same mutex as those fields.

S11 (iz/gerekçe, orta–zor) — sl. 59–60#

Filozof i'nin ihtiyacı çubuk i ve (i+1) mod 5. "Önce küçük numaralı çubuk" kuralı uygulanınca (a) hangi filozofun alma sırası "önce sol"dan farklılaşır? (b) Neden bekleme döngüsü oluşamaz? (c) Bu kural filozof 3'ün sonunda yiyeceğini garanti eder mi?

Cevabı ve ölçütü göster

Cevap (ideal). (a) Only philosopher 4: it needs chopsticks 4 and 0 and must take 0 first; philosophers 0–3 take i before i + 1, which is already lower-first. (b) A philosopher holding chopstick a waits only for a higher-numbered chopstick b > a. A cycle of waiting would require strictly increasing numbers all the way around and back to the starting number, which is impossible, so the circular acquisition pattern cannot form (provided everyone obeys the rule). (c) No. It removes this lock-order deadlock under the model, but it does not by itself prove bounded waiting or fair eating opportunities: neighbours could repeatedly win the shared chopsticks. Fairness needs a separate argument.

S12 (kısa cevap, orta–zor) — sl. 63, 62#

Yüksek öncelikli H'nin düşük öncelikli L'nin tuttuğu kilidi beklediği bir sistemde priority inheritance açılıyor. (a) Priority inheritance tam olarak ne yapar? (b) Aynı sistemde T1 lock(A); lock(B) ve T2 lock(B); lock(A) yaparken oluşan deadlock'u çözer mi? (c) Varsayılan bir pthread mutex'inin bu özelliğe sahip olduğunu varsayabilir miyiz?

Cevabı ve ölçütü göster

Cevap (ideal). (a) It temporarily raises the lock owner's effective priority (to that of the highest-priority waiter) so that medium-priority work cannot delay the owner; the owner finishes, releases, and H proceeds. It shortens the inversion; it is a specific protocol. (b) No. In the A/B case each thread waits for a lock the other blocked thread holds; raising priorities does not let either release. The cure is breaking the circular wait (e.g., a global lock order). (c) No. It is not an assumed property of default mutexes; it must be a supported, explicitly selected protocol.

S13 (hatayı bul, zor) — sl. 55, 68#

queue.c'nin üreticisinde kapanış şöyle yazılmış:

pthread_mutex_lock(&m);
closed = 1;                 /* no broadcast */
pthread_mutex_unlock(&m);

Tüketici değiştirilmemiş: while (count == 0 && !closed) pthread_cond_wait(&not_empty, &m);. Program her zaman takılır mı? Takıldığı bir iz verin ve gerekçeyi yazın.

Cevabı ve ölçütü göster

Cevap (ideal). Not always, but it can hang. If the consumer is still busy draining when closed is set, it later locks m, sees count == 0 and closed == 1, and exits normally. Hang trace: the consumer removes the last item (10,000), loops, locks m, sees count == 0 && !closed, and waits (releasing m). The producer then locks m, sets closed = 1 and unlocks without notifying. The consumer's predicate has become false, but nobody wakes it to recheck; it sleeps forever and main's join hangs. Closure is a state change that sleeping consumers must observe: set it under the mutex and broadcast so every waiter rechecks the termination predicate. "Sometimes works" is exactly what testing cannot rule out.

S14 (gerekçelendirme, zor) — sl. 32–33; kod/counter.c#

counter.c'nin split modunda:

long old = atomic_load(&acounter);
pthread_mutex_lock(&m);
arrived++;
if (arrived == 2) pthread_cond_broadcast(&cv);
while (arrived < 2) pthread_cond_wait(&cv, &m);
pthread_mutex_unlock(&m);
atomic_store(&acounter, old + 1);

(a) Bu kod iki store'dan önce iki load'un olduğunu nasıl garanti eder? (b) arrived neden mutex altında ve neden while? (c) İki thread varken broadcast yerine signal yeterli olur muydu? Thread sayısı 3'e çıkarılıp koşul arrived == 3/arrived < 3 yapılırsa?

Cevabı ve ölçütü göster

Cevap (ideal). (a) Each thread performs its atomic_load before entering the rendezvous, and no thread passes the rendezvous until arrived == 2, i.e., until both have loaded. So both loads (reading 0) precede both stores, which write 1: the final value is 1 with no C data race. (b) arrived is a shared counter whose increment and test form a compound operation; the mutex makes them indivisible and lets the condition wait release and reacquire it safely. while is required because a wakeup is not a guarantee: spurious wakeups are permitted, so the thread rechecks arrived < 2. (c) With two threads, when the second arrives at most one thread (the first) is waiting, so signal would wake it; broadcast is not required. With three threads, the third arrival must wake two waiters; a single signal may wake only one waiter (POSIX guarantees at least one); the other can then sleep forever. Broadcast lets every waiter recheck the predicate.

S15 (sentez/tasarım, zor) — sl. 12, 22, 28, 64#

Bir konser gişesinde 100 koltuk var. reserve(name): koltuk kaldıysa kalan koltuk sayısını bir azaltır ve buyers[sold] = name; sold++ yapar. Bir öğrenci şunu öneriyor: "seats_left'i atomic_int yapalım, if (atomic_load(&seats_left) > 0) atomic_fetch_sub(&seats_left, 1); yeter." (a) Bu öneride iki ayrı hata bulun. (b) Invariant'ı yazın. (c) Doğru tasarımı verin.

Cevap (ideal). (a) Error 1: "if seats remain, take one" is a compound protocol; with one seat left, two threads can both load 1, both fetch_sub, and seats_left becomes −1: an oversold seat. Error 2: even a correct atomic counter does not protect a multi-variable invariant: buyers[sold] = name; sold++ is a separate read–modify–write on shared state; two threads can write the same buyers slot and lose a name, and a reader can see seats_left decremented before the buyer is recorded. (b) 0 ≤ seats_left ≤ 100, sold + seats_left == 100, and buyers[0 … sold − 1] each hold exactly one recorded buyer. (c) One mutex protecting seats_left, sold and buyers; reserve locks, checks seats_left > 0, decrements, records the buyer and increments sold, then unlocks; reports take the same mutex for a consistent snapshot. (Alternative: a counting semaphore of 100 for admission plus the mutex for the buyer list.) A mutex is the clearest starting point for one invariant across several operations; an atomic operation suffices only for one independent numeric update.
